## Defects found and narrow corrections

Initial PostgreSQL race evidence showed that two concurrent stale requests for one confirmed sales order could both read the same unallocated line. Stock-row locking alone did not serialize that same order when on-hand capacity exceeded the order quantity; the test observed reservation quantity double the sales-order line allocation.

The service now locks and refreshes the `SalesOrder` row before allocate/cancel state checks. Allocation, cancellation release, and dispatch refresh locked stock/order-line identities under lock, preventing stale SQLAlchemy identity-map values from replacing current database values. Dispatch locks shipment, then sales order, then stock in a consistent order, revalidates the shipment after refresh, and flushes shipped-quantity increments before refreshing all lines to compute the order status. The changes preserve the existing allocation and shipment policies; they do not add a reservation schema or infer a new business rule.

Adversarial cases now cover same-order double allocation, competing orders for limited stock, a previously loaded stale stock row, cancellation after another transaction allocates while the cancel session has stale line state, and sequential partial shipments when the second request already holds a stale sales-line object.

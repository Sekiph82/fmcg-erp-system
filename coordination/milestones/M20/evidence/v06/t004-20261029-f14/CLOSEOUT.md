## V05-F14 remediation

`SHIFT_ADD` now requires a concrete date/start/end interval. The service verifies interval validity and that `hours` matches its duration; rejects overlap with configured calendar shifts and other additions; enforces total remaining daily capacity; and refuses to credit additions against missing or inconsistent calendars. If downtime exists but cannot be compared safely because the work center has no timezone mapping, the added capacity is reported as unresolved/unknown and is not credited. The what-if UI accepts start/end times and shows the derived duration.

A follow-up boundary check showed that a downtime event on the UTC day immediately before or after the local calendar date could otherwise be omitted. Since the work center has no timezone, the service now queries a conservative one-day UTC margin on both sides; any such downtime keeps added capacity unresolved rather than credited. The regression includes a previous-day event ending before UTC midnight and a next-day event beginning after the old query bound; separate what-if scenarios prove both remain uncredited through the PostgreSQL-backed service path.

The product standard-cost and scenario impact-currency checks now require three uppercase ASCII letters in PostgreSQL. Migration `20261029_0025` replaces the looser “three uppercase characters” checks. If legacy rows contain malformed currency strings, migration preserves them and leaves that specific constraint `NOT VALID`; new or changed malformed rows are rejected. What-if costing reports malformed legacy currency as unknown. A disposable legacy-row migration check verified preservation, unknown costing, rejection of a new malformed value, and successful later constraint validation after the synthetic row was normalized. SQLite retains its portable legacy check expression; PostgreSQL uses the strict alphabetic check.

## Synthetic MRP → MPS cross-module regression (2026-10-29)

The cross-module PostgreSQL scenario now creates a synthetic confirmed sales order and executes the real MRP service before generating the MPS plan. Its deliberately competing supplies prove that MRP counts only the remaining quantity of open production orders in the run's warehouse and planning horizon: the same-warehouse order contributes `1.000 - 0.250 = 0.750 KG`; a `100 KG` order in another warehouse and a `100 KG` order after the horizon contribute nothing. For `5.000 KG` demand, MRP therefore records `0.750 KG` incoming production and `4.250 KG` net/suggested production; the generated MPS line is `4.250 KG`.

This exercise exposed that the incoming-production query used a nonexistent `ProductionOrder.target_quantity` field. It now aggregates `max(planned_quantity - coalesce(actual_quantity, 0), 0)`, applies the inclusive planning-horizon boundary, and filters by the MRP run warehouse when one is selected. The regression then carries the result through BOM/stock diagnostics, what-if scenarios, release and replay. It checks the live `4.250 KG` plan line remains unchanged by what-if simulation.

Fresh task-owned PostgreSQL 16 evidence is in `m20-p0-and-cross-module-postgres-20261029-first-attempt.log` (migration setup and the first attempt) and `m20-p0-and-cross-module-postgres-20261029-retry01.log` (final rerun). The passing disposable database was `fmcg_m20_t004_eab1e5d284764d2995892c8703036537` on loopback port `61595` using local trust authentication; no database password was used. The bounded rerun of the scoped-plan isolation, what-if permission/lifecycle and MRP→MPS cross-module tests passed **3/3 (69 warnings)**.
